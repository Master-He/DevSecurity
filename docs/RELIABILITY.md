# 可靠性

## 服务目标（建议，待确认）

- 平台 API：99.9%/月可用性；
- 创建扫描请求：失败率 < 1%（排除用户输入和权限错误）；
- 常规查询：P95 < 500 ms；
- 扫描任务：允许排队，状态必须可观测且不会永久卡在 `running`；
- 漏洞数据镜像：同步失败时继续服务并暴露数据滞后；
- 对象存储：原始报告和扫描结论分离，丢失报告不应删除结论。

这些是设计目标，不是已签署 SLA。

## 故障处理

**Runner 崩溃/失联**

租约过期后任务按策略重试，旧的 attempt 标记失败；不覆盖历史结果。超过最大次数进入可操作失败状态。

**数据库不可用**

API 返回明确错误，不缓存并伪造写成功；已在执行的任务完成本地产物后按保留策略等待上传，不得无限占用源码。

**对象存储不可用**

扫描可以进入 `partially_succeeded`，但必须提示证据/报告缺失；不得把无法保存结果称为成功。

**首次 Compose 启动时镜像拉取失败**

`docker compose up --build` 不会进入业务服务启动阶段。常见原因是 `registry-mirrors` 失效或 Docker Desktop 代理不可用，日志会包含 `failed to resolve reference`、`TLS handshake` 或 `EOF`。使用 `docker pull postgres:16-alpine` 可快速区分环境网络问题与项目编排问题。

**扫描引擎 OOM/超时**

杀进程组、清理临时目录、记录资源诊断；不自动无限重试资源耗尽任务。

**漏洞库陈旧**

继续使用最后签名快照，项目页面和扫描摘要显示陈旧时间；超过策略阈值时禁止宣称扫描已完整。

**Webhook 接收方故障**

指数退避、最大次数、死信可观察和人工重放；业务主流程不等待接收方。

## 备份与恢复

- PostgreSQL 每日全量 + 持续 WAL/PITR（生产部署时确定）；
- 对象存储版本/生命周期和独立备份；
- 配置、策略、规则 profile 和 Secret 引用有版本；
- 每季度至少一次恢复演练，验证任务、结果和权限可恢复；
- 恢复演练不得把真实源码复制到非受控环境。

## 可观测性

必须监控：

- 队列长度、最老任务年龄、运行任务数、租约回收次数；
- 各状态转换和失败码；
- 扫描时长、CPU/内存、引擎退出码；
- 结果批次延迟、对象存储错误；
- 数据同步成功率、数据滞后；
- Webhook 重试和死信；
- 认证失败、403、审计写入失败；
- IAST Agent 心跳、过期未回收、性能预算；
- DAST 目标范围拒绝和出口代理阻断。

日志使用结构化字段和 request ID；禁止记录完整源码、请求体、Cookie 和 Secret。
