# Finding 生命周期

## 目标

让研发和安全团队对同一个问题达成可追溯的处理结论，同时保留引擎原始发现，避免误报或风险接受造成事实丢失。

## 状态

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| open | 新发现或到期重新打开 | 确认/修复/误报/接受风险 |
| triaged | 已确认并指派/设置优先级 | 修复、误报、接受风险 |
| fixed | 有后续扫描证明消除，或人工提供证据 | 复现则重新打开 |
| false_positive | 复核认为检测不适用 | 证据变化或复核撤回 |
| accepted | 有审批、理由和到期日 | 到期、风险变化或撤销 |
| withdrawn | 漏洞源撤回/组件不再受影响 | 数据源恢复或新证据 |

## 关键行为

- 引擎更新或重新扫描可能产生新的 occurrence；同一 fingerprint 的处置不能无条件吞掉新的根因。
- 人工状态变更均写 `FindingEvent`，包含操作者、前后状态、理由和证据。
- 接受风险必须设置到期日；到期自动变为 `open` 并通知负责人。
- “误报”不等于删除原始扫描记录；下载/API 仍能追溯来源。
- 批量操作需显示影响数量和匹配条件，避免误处理。
- 重新打开保留历史，不修改旧事件。

## 优先级

严重性来自引擎/数据源；平台可基于置信度、传播、项目等级和例外计算处置优先级。必须展示计算输入与策略版本，不能只给神秘总分。

## 验收

- 跨项目用户不能修改不属于自己的 Finding。
- developer 可提交误报申请但不能自行审批高风险接受。
- 到期风险自动恢复为 open，发送一次通知，并保留审批历史。
- 同一根因多次扫描不生成无限重复列表，但新 occurrence 仍可查看。
- 导出 SARIF/JSON 不丢失平台需要的规则、位置和状态映射。
