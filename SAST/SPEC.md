# SAST 引擎 SPEC

状态：Joern CPG 接入骨架已创建，规则查询和结果映射尚未实现。

当前只承诺：

- `SAST/joern-adapter` 能检查 Joern CLI；
- 接收 ZIP 并调用 `joern-parse` 生成 CPG；
- Joern 不可用或失败时返回明确错误；
- 不把只有 CPG 构建成功解释成漏洞扫描完成。

## 1. 目的

对源代码和必要构建产物执行静态分析，发现注入、认证绕过、敏感信息、不安全反序列化、路径穿越、加密误用等风险。通过统一适配层调度成熟开源引擎，保留规则、数据流证据和置信度，供平台去重与展示。

## 2. 设计立场

SAST 涉及多语言语义、跨文件数据流、框架建模和大量误报治理，不适合在立项阶段从零实现通用规则引擎。首版选择“开源引擎 + 统一适配器 + 公司规则策略”的方式，基于真实代码基准决定引擎组合。

## 3. 语言优先级

建议默认值，待 Q-004 确认：

| 优先级 | 语言 | 最低能力 |
|---|---|---|
| P0 | Java/Kotlin | 跨文件污点流、常见 Web 框架、反序列化 |
| P0 | JavaScript/TypeScript | Node、浏览器端危险 sink、依赖注入风险 |
| P0 | Python | Django/Flask/FastAPI 常见模式、命令/模板/SQL 风险 |
| P0 | Go | HTTP 输入到 SQL/命令/路径的流 |
| P1 | C# | ASP.NET 和常见序列化风险 |
| P1 | Ruby | Rails 常见模式 |
| P1 | PHP | 常见 Web 框架 |
| P2 | C/C++、Rust、Shell、IaC | 根据实际资产决定，不承诺完整数据流 |

语言支持必须通过样本仓库验证，不能仅依据厂商宣称的语法支持。

## 4. 扫描模式

- **仓库全量扫描**：固定 commit，建立全项目上下文。
- **增量扫描**：按 diff 路由到受影响文件，同时保留必要的调用/配置上下文。
- **规则集扫描**：安全团队选择的规则 profile，可包含组织自定义规则。
- **编译型项目扫描**：允许在隔离 Runner 中构建，但不得执行不可信构建脚本中的凭据或外联操作。

默认输出所有发现的未过滤结果；通知和门禁可使用项目策略过滤，但不得删除审计所需事实。

## 5. 功能需求

### 5.1 项目接收

- 支持固定 Git revision 和源码归档。
- 验证归档路径、符号链接、文件类型、体积和文件数量。
- 识别语言、构建系统和可分析入口，不把第三方 vendor 目录无条件当作业务代码。
- 对自动生成代码、测试代码、依赖库生成排除标记，规则集可覆盖。
- 记录引擎版本、规则版本、配置哈希和输入 commit。

### 5.2 引擎适配

候选开源引擎在基准测试后组合使用：

- **Semgrep CE**：多语言规则覆盖、部署简单、SARIF/JSON；
- **CodeQL**：跨过程数据流强，但需评估许可证和 CI 运行成本；
- **Joern**：代码属性图和自定义查询，需评估语言与工程成本；
- **Bandit、gosec、RuboCop Security 等**：作为语言专项补充或基准对照。

引擎选择是待验证决策，不在本 SPEC 中假定许可允许商业内网使用。每个引擎必须有独立适配器、版本锁定和开关。

适配器职责：

- 生成引擎配置，不拼接未转义 shell 命令；
- 将项目/规则过滤映射为引擎原生配置；
- 限制 CPU、内存、子进程和输出大小；
- 捕获结构化报告、日志和退出码；
- 将记录映射为统一 Finding，保留原始规则 ID 和位置权限；
- 输出引擎级别诊断，区分“未发现问题”和“引擎没跑完”。

### 5.3 规则治理

- 内置规则来自引擎时记录来源、许可证和版本。
- 公司规则有唯一 ID、描述、严重性、适用语言、样本和负责人。
- 规则更新需要基准样本回归，防止大量误报或漏报。
- 支持按项目选择 profile；profile 变更产生审计记录。
- 不把抑制注释当作安全结论；仍记录原始发现和抑制原因。

### 5.4 结果标准化

- 每条 Finding 包含规则 ID、标题、类别、严重性、置信度、CWE、位置和修复建议。
- 支持多位置证据：source、sink、传播点、配置文件和调用链；按稳定顺序输出。
- 对同一根因的不同引擎报告做聚类，但保留每个引擎 occurrence。
- 路径统一转换为仓库相对路径，不泄露 Runner 临时目录。
- 自动修复建议只能作为建议，不得未经用户确认直接改写用户代码。

## 6. 基准与选型方法

建立至少三类固定样本：

1. **安全样本**：已知漏洞和已修复版本，验证召回；
2. **误报样本**：合法反射、参数化查询、框架内置防护；
3. **规模样本**：多模块、多语言、大型依赖目录，验证性能。

评估维度：

- 首期语言的真实召回/误报；
- 跨文件/跨过程能力；
- 构建要求和离线可用性；
- 规则可维护性和 SARIF 兼容性；
- CPU/内存/耗时和并发能力；
- 许可证、商业使用和安全漏洞响应；
- 升级成本与社区活跃度。

建议只在基准完成后确定主引擎，避免“先绑定工具，后寻找用例”。

## 7. 输出契约

输出统一 Finding、原始引擎报告和 `diagnostics`。批量结果可使用 NDJSON，单次完整结果必须是版本化 JSON。字段见 [../docs/design-docs/scan-result-model.md](../docs/design-docs/scan-result-model.md)。

每个 Finding 必须能追溯到：

`engine version + rule id + rule revision + input revision + absolute-independent relative location`

## 8. 非功能与安全要求

- Runner 默认断网，构建模式只开放必要镜像仓库/代理。
- 不挂载 Docker socket、Kubernetes service account token 或宿主机凭据。
- 对 YAML、源码和报告设置大小/超时限制。
- 引擎崩溃返回明确错误，不输出空结果冒充成功。
- 临时源码和编译缓存隔离，任务完成后删除。
- 不使用生产环境凭据构建或运行扫描。
- 原始报告仅授权用户可下载，普通查看使用脱敏后的标准化结果。

## 9. 测试与验收

- 每个 P0 语言的漏洞/安全/误报黄金样本可重复执行。
- 同一 revised commit 的全量扫描可追溯到规则版本与报告校验和。
- 引擎超时、OOM、退出码异常、报告损坏时有明确诊断。
- 多引擎同一根因可聚合并保留 occurrence。
- 增量扫描至少正确分析 diff 触及的规则和上下文；无法保证时退回全量。
- 扫描结果不再包含 Runner 路径、密钥或源码全文。

## 10. 里程碑

1. 收集合法脱敏样本和公司主语言清单。
2. 对 2-3 个候选引擎完成同样基准测试。
3. 实现一个主引擎适配器和统一 Finding。
4. 完成 SARIF 导入/导出和多引擎聚合。
5. 建立规则发布、回归和回滚流程。

暂不在本阶段实现扫描代码。
