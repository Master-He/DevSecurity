# IAST 引擎 SPEC

## 1. 目的

在已授权的测试应用内部运行轻量 Agent，结合真实测试流量和应用内部执行上下文（调用栈、配置、数据流），发现运行时漏洞并减少纯黑盒扫描的不可见性。

IAST 是高侵入能力：Agent 可能造成应用崩溃、性能下降或敏感数据进入遥测。平台必须把环境授权、卸载和资源保护作为核心功能。

## 2. 范围

MVP：

- 非生产测试环境的应用注册；
- Agent 安装、启动、心跳、任务关联和卸载；
- 面向 HTTP 测试流量的污点跟踪或运行时规则检测；
- Finding 与部署版本、测试会话、请求和调用栈关联；
- 结果上传、脱敏、主动过期和清理。

后续：

- 与自动化测试框架和 API 回归用例联动；
- 多角色、多服务链路追踪；
- 生产只读监测作为独立产品决策，不在 MVP 范围。

非目标：

- 秘密监视用户或收集生产业务数据；
- 在宿主应用内执行任意插件；
- 用 IAST 高频注入/攻击业务系统；
- 把 Agent 当作无审计的远程控制通道。

## 3. 运行模式

### 3.1 Agent 模式

通过语言 Agent/字节码插桩或运行时 hook 收集：

- HTTP 入口、路由、参数来源；
- 关键 sink 与调用栈；
- 污点传播或运行时安全检查；
- 当前应用版本和环境标签。

### 3.2 测试模式

由已授权的自动化测试或 DAST 流量触发。IAST 只观察并分析流量，不绕过认证，不主动扩大测试范围。平台记录测试会话 ID，便于把发现映射到扫描任务。

### 3.3 部署模式

Agent 必须在短生命周期测试 Pod/进程中挂载，不能污染生产镜像。建议使用 sidecar/init 或专用测试镜像；所有 artifact 有签名和固定版本。

## 4. 授权与环境生命周期

`IASTEnvironment` 至少包含：

- 所有者、应用、版本/镜像 digest、环境名称；
- 允许的运行时、框架版本和 Agent 类型；
- 生效时间、到期时间、自动卸载开关；
- 允许的测试会话和流量来源；
- 数据保留策略；
- 租户/项目权限和审批记录。

创建环境时：

1. 验证用户和项目的 `iast:deploy` 权限；
2. 验证环境标签不是生产（除非后续单独批准）；
3. 生成短时注册令牌和唯一 Agent ID；
4. 设置定时回收和最大会话时长；
5. 记录部署镜像 digest、配置哈希和审批人。

任务结束、Agent 失联超限或环境过期都触发回收，并产生审计事件。

## 5. 支持矩阵

必须是实测矩阵，不能把语言层面的“支持”扩大为所有框架：

| 优先级 | 运行时 | 首版范围 |
|---|---|---|
| P0 | Java/JVM | Spring Boot 常见 HTTP/数据访问链路 |
| P0 | Node.js | Express 常见请求链路 |
| P1 | .NET | ASP.NET Core |
| P1 | Python | WSGI/ASGI 常见框架 |
| P2 | Go | 编译插桩方案需专项验证 |
| P2 | PHP | 根据业务资产决定 |

每个运行时需锁定 JVM/Node/.NET/Python 版本、框架版本和进程内存/CPU 影响基线。

## 6. 核心功能

### 6.1 Agent 管理

- 一次性注册令牌换取短期 Agent 身份；
- mTLS 或短期签名上传通道；
- 心跳、配置版本、健康状态和卸载确认；
- Agent 版本与规则版本固定，支持紧急禁用；
- 失败、失联、超时和卸载后的资源回收记录。

### 6.2 运行时检测

- 从 HTTP 请求/框架入口识别污点源；
- 跟踪到 SQL、命令、模板、文件、反序列化、SSRF 等 sink；
- 保留 source、传播链、sink、调用栈和防御函数信息；
- 过滤明确安全编码或已验证防护，但保留原始证据；
- 对多线程/异步上下文使用独立 correlation ID，避免串数据。

### 6.3 数据上传与脱敏

- 默认只上传最小证据，不上传完整请求体、Cookie 或响应体；
- 参数值可哈希或截断，敏感字段按规则脱敏；
- 原始源码片段只保存必要的少量行，并按对象存储权限访问；
- Agent 与控制面之间采用压缩、限流和背压，避免拖慢应用；
- 数据丢失时必须报告采集不完整，而非返回无缺陷。

## 7. 结果

Finding 额外包含：

- runtime、agent version、应用版本/镜像 digest；
- test session ID、服务名、方法和路由；
- source/sink 类型和调用链；
- 防护函数、污染置信度和运行时证据引用。

同一漏洞在不同请求的 occurrence 聚合，避免每个请求生成一条告警。应按 endpoint + parameter + sink + rule 做稳定指纹。

## 8. 安全与非功能要求

- Agent 默认只出站到指定平台地址，不接收任意远程命令。
- Agent 安装包和配置签名；禁止从目标应用工作目录加载可篡改脚本。
- 测试环境必须与生产网络隔离；默认禁止横向扩展到其他服务。
- 对 Agent 开销设置上限，超过阈值自动降级并告警。
- Agent 必须有硬超时、停止采集和卸载路径。
- 平台不得在应用内持久化用户账号、密钥或完整业务数据。
- 每个 Agent 的日志和结果只允许项目授权用户访问。

## 9. 测试与验收

- 使用本地靶场验证常见 source-to-sink 传播和安全样本；
- 验证多线程/异步下不存在数据串流；
- 验证 Agent 安装、心跳、失联、过期和一键卸载；
- 验证非授权环境不能获取注册令牌；
- 验证 Cookie、密码和业务数据不会出现在日志/报告中；
- 验证应用崩溃、Agent 崩溃、存储满时能安全降级；
- 建立 CPU、内存、请求延迟开销基线。

## 10. 里程碑

1. 确定第一个运行时和框架，搭建靶场。
2. 完成 Agent 生命周期和受控卸载。
3. 完成最小污点检测和结果标准化。
4. 完成性能、隐私和失联回收测试。
5. 在单一非生产业务环境试点。

本阶段只写规格，不实现 Agent 或服务端代码。
